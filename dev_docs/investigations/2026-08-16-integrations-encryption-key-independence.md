## What's confirmed by reading the code (`lib/phoenix_kit/integrations/`)

1. `PhoenixKit.Integrations.Encryption` — AES-256-GCM, `enc:v1:` prefix.
   Fields: `access_token`, `refresh_token`, `client_secret`, `api_key`,
   `bot_token`, `secret_key`, `password`.
2. The encryption key is `SHA256("phoenix_kit_integrations:" <> secret_key_base)`
   — `secret_key_base` is the ONLY root secret; no independent key exists today.
3. `secret_key_base` resolution: flat `config :phoenix_kit, secret_key_base:`
   first, else the host app's own Endpoint `secret_key_base` (most hosts hit
   this fallback — the installer never stamps the flat key).
4. No rotation path exists. The moduledoc says so explicitly: rotating
   `secret_key_base` makes every `enc:v1:` value undecryptable, no re-wrap.
5. `integration_encryption_enabled: false` disables encryption with **zero**
   signal anywhere — no boot warning, no admin UI indicator. Confirmed by
   `grep`: `Encryption.enabled?()` / `.status()` is not called anywhere
   outside the module itself and its own tests.
6. **A second, previously undocumented silent-failure bug**, found while
   tracing the decrypt path per the owner's "does this code ever actually
   fire" instruction: `Integrations.Encryption.maybe_decrypt_field/4` on a
   decrypt failure (`{:error, _}`) returns the accumulator **unchanged** —
   i.e. it hands back the raw `"enc:v1:base64..."` ciphertext string as if it
   were the live credential value, with no log line. Trivially reproducible:
   encrypt a field, change the active key, decrypt — the caller gets a
   garbled string it will treat as a real access token / API key with zero
   indication anything went wrong. This directly undermines both the
   rotation work (a rotation that misses rows fails silently) and the
   "явное предупреждение" requirement for the disabled-encryption case, so
   it's in scope alongside the four numbered items.

## Design

### 1. Dedicated key, decoupled from `secret_key_base`

`lib/phoenix_kit/integrations/encryption.ex` — key resolution is now tiered:

1. **Dedicated** — `config :phoenix_kit, :integrations_encryption_key` (new
   config key, added to `PhoenixKit.Config`'s `@default_config`). Recommended
   wiring: `System.get_env("PHOENIX_KIT_INTEGRATIONS_ENCRYPTION_KEY")` in
   `runtime.exs`, value generated by the new mix task (below).
2. **Legacy** — the old `secret_key_base`-derived key, kept as a fallback for
   backwards compatibility (existing installs must not go dark on upgrade).
3. **None** — encryption disabled (explicitly, or no key resolves at all).

`Encryption.status/0` reports which tier is active
(`:dedicated | :legacy_secret_key_base | :disabled_no_key |
:disabled_explicit`) without touching the database — safe to call from a
`mount/3` or a boot hook.

Absent-new-secret behavior (the "не тихо взять secret_key_base" requirement):
the legacy fallback still WORKS (an app must not silently break on upgrade),
but it is never silent about it — see (3) below. This was a deliberate choice
between "explicit refusal" and "explicit warning" per the contract's own
wording (either is acceptable); refusal would mean every existing install
goes dark for integrations on upgrade with no migration path, which is a
worse outcome than a loud, persistent warning plus a one-command fix
(`mix phoenix_kit.integrations.rotate_key`).

### 1b. Silent decrypt-failure bug (elevated to equal priority, per owner)

`maybe_decrypt_field/4` used to return its accumulator **unchanged** on a
decrypt failure — handing back the raw `enc:v1:...` ciphertext as if it were
the live credential, with no log line. Fixed: a decrypt failure now logs
`Logger.error` (field name + reason, never the ciphertext or key material)
and drops the field entirely, so `data["api_key"]` etc. is `nil`/absent
instead of a garbled string a caller would otherwise send to a third-party
API as a bogus Bearer token. Verified red-then-green (see "Verification"
below) — this is the single highest-value fix in the PR, since every other
guarantee (rotation correctness, "explicit warning not silent fallback")
depends on decrypt failure actually being visible.

### 2. Rotation

New module `PhoenixKit.Integrations.KeyRotation` (`rotate/2`): decrypts every
stored connection under whatever key is CURRENTLY active, verifies every row
succeeds, and — only if ALL rows are readable — re-encrypts all of them under
a new secret inside a single DB transaction (all-or-nothing; a mid-way
failure rolls back rather than leaving a mixed-key fleet). `dry_run: true`
runs the verify pass with no writes.

New mix task `mix phoenix_kit.integrations.rotate_key` wraps it:
`--dry-run`, `--new-key=<secret>` (else generates one), prints the secret
once and the config to set. Covers both "first adoption" (migrate off the
legacy tier) and "suspected compromise" (rotate an existing dedicated key).

### 3. Visibility of disabled/weak encryption

- **Boot**: `PhoenixKit.Supervisor` runs `Encryption.warn_if_insecure/0` once
  as a fire-and-forget `Task` child (same pattern as the existing
  `auto_grant_admin_permissions` / `normalize_languages` checks), AFTER the
  host's Repo/Endpoint have started — NOT in `PhoenixKit.Application.start/2`,
  which runs before the host Endpoint exists and would false-positive on
  every install using the (common, supported) `secret_key_base` fallback.
  Silent for the healthy `:dedicated` case; `Logger.warning` otherwise.
- **Admin UI**: `/admin/settings/integrations/website` (the system
  integrations page) shows an `alert alert-warning` banner (same visual
  pattern as `email_sending.html.heex`'s sender/mailer warnings) whenever
  `Encryption.status() != :dedicated`. Scoped to the admin/system page only —
  not the personal integrations page, which regular (non-admin) users can
  reach; showing key-management internals there would be an inappropriate
  disclosure to non-admins for what is a system-level operational fact.

## Environment notes (this container — not relevant to the PR itself)

- `MIX_ENV` is set to `dev` ambiently for this container's shell (for the
  tmux `iex -S mix phx.server` panels) — `mix test` respects an explicitly-set
  `MIX_ENV` instead of forcing `:test`, so `test/support` (ConnCase, DataCase,
  TestRepo) silently never compiled until `MIX_ENV=test` was passed
  explicitly. `mix precommit`/`mix quality`/dialyzer, conversely, are meant to
  run under the DEFAULT (dev) env — running them under a forced `MIX_ENV=test`
  built a bogus "-test.plt" that produced spurious `unknown_function` noise
  for `ExUnit.Callbacks.*`. Lesson: pass `MIX_ENV=test` only for `mix test`
  itself, never for `precommit`/`quality`/`dialyzer`.
- `PGHOST`/`PGUSER`/`PGPASSWORD`/`PGDATABASE` are ALSO set ambiently by
  something in this container's process-spawn path (`PGHOST=postgres`,
  `PGDATABASE=phoenix_kit_dev`, ...) — invisible to a plain `env` in the bash
  tool's own shell, but visible to `System.get_env/1` inside the spawned
  `mix`/BEAM process. Left alone, `mix test` silently pointed at the wrong
  database. Fix: export all five PG* vars explicitly
  (`PGHOST=127.0.0.1 PGUSER=postgres PGPASSWORD=postgres
  PGDATABASE=phoenix_kit_test PGPORT=5432`) — `127.0.0.1`, not `localhost`,
  because `localhost` intermittently resolved to `::1`, which this Postgres's
  `pg_hba.conf` treats differently (requires a real password) than `127.0.0.1`
  (trusted). A stale/half-migrated `phoenix_kit_test` from an earlier
  interrupted run also needed `mix test.reset` once.

## Round 1 review (checker `pi`, tools-off) — verdict FIX, 11 findings

Full text: `S001-VERDICT-r1.txt` (session-local, deleted when done, not part
of this PR). Summary of triage and fixes, ranked by the checker's own
priority ordering (not the numbering in the verdict file):

1. **CRITICAL, fixed** — `mix phoenix_kit.integrations.rotate_key` parsed
   args with `OptionParser.parse(argv, switches: @switches)` (non-strict).
   An unrecognized/misspelled flag — `--dryrun` instead of `--dry-run` — is
   silently accepted under its OWN wrong key in non-strict mode, so
   `Keyword.get(opts, :dry_run, false)` defaulted to `false` and a REAL
   rotation ran instead of the dry run the typo was reaching for. Switched
   to `strict:`, added an `{:error, message}` path that `Mix.raise`s
   instead of proceeding. Verified live on Hydroforce: `--dryrun` now fails
   at argument parsing (`** (Mix) Invalid option(s): --dryrun`) before
   `app.start` even runs — no DB touched. Unit test:
   `test/mix/tasks/phoenix_kit_integrations_rotate_key_test.exs`.
2. **minor, fixed** — `--new-key=""` is truthy under `||`, so an empty
   string reached `KeyRotation.rotate/2`'s `new_secret != ""` guard and
   crashed with `FunctionClauseError` instead of generating a real secret
   as the caller obviously intended. `resolve_new_secret/1` now treats an
   empty string the same as an omitted flag.
3. **major, fixed** — `key_rotation.ex` read rows via a plain `repo.all()`
   OUTSIDE any transaction, then wrote a re-encrypted snapshot back inside a
   SEPARATE transaction later. A concurrent write in between (most
   plausibly an OAuth token auto-refresh calling `save_setup/4`) would be
   silently clobbered by rotation's stale snapshot — a lost-update race.
   Fixed: the fetch is now `SELECT ... FOR UPDATE` INSIDE the same
   transaction that performs the write, so a concurrent writer blocks
   instead of racing. Verified by fact, not claim: `locked_rows_query/0` is
   exposed `@doc false` and a test runs it through

   released) was NOT attempted — that needs two independently-committing
   connections coordinated around the lock, which is more infrastructure
   than a single-process ExUnit test provides. This project already makes
   that exact call for an analogous scenario
   (`PhoenixKit.Integration.RepairTest`'s S18, documented in that file's
   moduledoc as "more infrastructure than a single-process ExUnit test
   naturally provides") — followed the same precedent rather than inventing
   new infrastructure for this PR.
4. **major, fixed (docs)** — the rotation→restart gap was documented only
   from the READ side ("reads will fail until you restart"). A WRITE
   landing in that window (again, an OAuth auto-refresh) saves under the
   still-active OLD key into a row already moved to the NEW secret, and
   that write is just as lost once the app restarts onto the new key.
   `KeyRotation`'s moduledoc and the mix task's moduledoc both now say this
   explicitly and recommend treating the window as a brief maintenance
   window, not a fire-and-forget step. No dual-key runtime fallback was
   added to close the gap in code — that would silently mask exactly the
   failure class this whole PR exists to make loud.

## Round 2 review (checker `pi`, tools-off) — verdict FIX, 4 findings

Full text: `S001-VERDICT-r2.txt` (session-local, deleted when done, not part
of this PR). One major finding — about the honesty of a claim, which this
whole engagement cares about specifically — plus three minor ones.

1. **MAJOR, fixed by honest downgrade, not by closing the gap.** Round 1's
   `key_rotation.ex` moduledoc claimed the row lock means "no write is
   ever lost to a lost-update race." False as stated: `FOR UPDATE`
   defends exactly ONE direction — a writer already mid-transaction when
   rotation tries to lock blocks, so rotation always re-encrypts the
   latest committed value. It does NOT defend the other direction: a
   writer that already READ a row (has old field values in memory) BEFORE
   rotation locked it still applies its `UPDATE` AFTER rotation commits,
   carrying content re-encrypted under the OLD key — silently reverting
   that row's rotation. `rotate/2` already reported success by then. The
   checker asked to verify a fact first: does `PhoenixKit.Settings.Setting`
   carry a `lock_version` (optimistic-lock) field? **Checked — no** (same
   fact confirmed twice, round 1 and round 2). That rules out the cheap
   optimistic-locking fix without a new migration touching every settings
   row in every install (not scoped to integrations). The other real fix —
   making every other `PhoenixKit.Integrations` write path
   (`save_setup/4`, `disconnect/3`, `record_validation/3`,
   `rename_connection/4`, `refresh_access_token/1`) also read-lock inside
   a transaction — would touch hot, already-shipped write paths well
   beyond what a rotation feature should carry in the same PR. Chose the
   checker's own explicitly-sanctioned third option: **downgrade the
   claim to what the code actually provides, and make running a real
   rotation as a maintenance-window operation an explicit, unmissable
   requirement** — both `KeyRotation`'s moduledoc and the mix task's
   moduledoc now spell out exactly which direction is defended, which
   isn't, and why, with "pause anything that writes to integration
   connections before rotating for real" stated as a requirement, not a
   suggestion.
2. **minor, fixed** — `rotate/2`'s guard was a blocklist
   (`status in [:disabled_no_key, :disabled_explicit] -> refuse`), so an
   unrecognized future `status/0` value would fall through the catch-all
   and be treated as safe to rotate — fail-open on the status enum, same
   class of bug as everything else in this engagement, just relocated.
   Flipped to an allowlist (`status in [:dedicated, :legacy_secret_key_base]
   -> proceed`, everything else refuses).
3. **minor, fixed** — round 1 fixed `--new-key=""` by treating it like the
   flag was never passed (generate a fresh secret) — the checker correctly
   called that fix itself risky: a script doing `--new-key="$MAYBE_UNSET"`
   with an empty variable would silently rotate under a RANDOM secret the
   caller never chose, printed to stdout exactly once and gone if that
   output isn't captured. Changed to reject an explicitly-empty `--new-key`
   outright (`Mix.raise`, same as an unrecognized flag) rather than
   silently substituting different behavior for a value the caller DID
   supply, just empty.
4. **minor, fixed** — round 1's dry-run fix routed through the SAME
   `FOR UPDATE`-locked transactional path as a real rotation (rolling back
   instead of committing), so "just looking" took a lock on every
   integration row for the full decrypt-verify pass — a real, if brief,
   side effect on live traffic that a dry run should never have. Split
   `do_rotate/2` into two paths: dry-run now does one plain, unlocked
   `repo.all/1` with zero transaction and zero side effects; only a real
   (non-dry-run) rotation takes the lock. Added
   `KeyRotation.rotate_rows_query/0` (unlocked) alongside the existing
   `locked_rows_query/0`, and a test asserting the dry-run query's SQL
   does NOT contain `FOR UPDATE` (sibling to round 1's test that the real
   query DOES).

Not attempted, deliberately, matching this project's own precedent
(`PhoenixKit.Integration.RepairTest`'s S18 note): a genuine two-connection
test that drives the still-open race in finding 1 to completion (one
transaction actually blocking on the lock, a second observing the outcome
after release). That needs two independently-committing connections
coordinated around the lock — more infrastructure than a single-process
ExUnit test provides, and not warranted for a gap the fix is to document
honestly rather than to close.

## Round 4 review (independent checker, live test DB) — verdict FAIL, spec-compliance stage

Full findings came from the orchestrator's own prompt, not a separate
verdict file. One critical, one major (framed as documentation), plus a
test-coverage gap — fixed in commits after `531829d3`.

1. **CRITICAL, fixed** — `Encryption.maybe_decrypt_field/4`'s round-1 fix
   (`encryption.ex:261`, `Map.delete(acc, field)` instead of returning
   `acc` unchanged) correctly stopped a decrypt failure from handing back
   raw ciphertext as a usable value, but broke something round 1 didn't
   consider: every write path in `PhoenixKit.Integrations` reads a row
   through `resolve_uuid/2`, merges new attributes onto the decrypted
   result, and writes `value_json` back WHOLESALE via `save_integration/2`.
   A field dropped from that merge base because it couldn't decrypt — not
   because any caller meant to remove it — was permanently erased by the
   very next write to the row, including fully automatic ones
   (`record_validation/3`, driven by `record_refresh_failure/2` and
   `maybe_record_recovery/1` on every OAuth token-refresh attempt, no
   operator involved). Before this bug, a temporary key mismatch was
   reversible (the ciphertext just didn't decrypt); after it, the field was
   gone for good the moment anything else wrote to that row — undermining
   the whole point of `KeyRotation`.

   Fixed with a write-side-only counterpart, not by touching the read path:
   `Encryption.decrypt_fields_with_failures/1` returns the same safe,
   ciphertext-never-exposed map `decrypt_fields/1` always has, plus the
   list of field names that failed to decrypt. `resolve_uuid/2` threads
   that list to every merge-based write call
   (`save_setup/4`, `exchange_code/4`, `refresh_access_token/1`,
   `rename_connection/4`, `record_validation/3`); `save_integration/3`'s
   new third argument restores each such field's untouched ciphertext from
   `setting.value_json` into what gets WRITTEN — never into what's
   returned to the caller, so a carried-forward field is never exposed as
   a usable value even transiently in a LiveView's assigns. A caller that
   deliberately rebuilds a smaller shape from scratch
   (`disconnect/3`'s allowlist) passes no failure list — those fields are
   meant to be gone regardless of whether they currently decrypt, and nothing
   second-guesses that. TDD: `test/integration/integrations_encryption_write_safety_test.exs`
   proves a field survives an unrelated write (and that disconnect still
   correctly removes what it means to remove); `encryption_test.exs` gained
   a `decrypt_fields_with_failures/1` describe block.

2. **MAJOR (docs), fixed** — `PhoenixKit.Supervisor`'s boot check comment
   claimed the encryption-status check ran "after the host's Endpoint has
   started". False for the actual, installer-mandated child order:
   `mix phoenix_kit.update`'s own ordering fix
   (`lib/mix/tasks/phoenix_kit.update.ex`, "PhoenixKit.Supervisor must
   start BEFORE Endpoint so Presence ETS tables are ready when LiveViews
   mount") places `PhoenixKit.Supervisor` — and therefore this Task child —
   BEFORE the host's own Endpoint, confirmed live in Hydroforce's own
   `application.ex` (`PhoenixKit.Supervisor` at line 15, Endpoint at line
   28). At that point `Endpoint.config/1` raises (config ETS table doesn't
   exist yet), rescued to `nil` in `Encryption`'s endpoint lookup, and
   `status/0` misreports `:disabled_no_key` instead of the true
   `:legacy_secret_key_base` for the majority of installs (the ones relying
   on the endpoint-fallback secret_key_base, since the installer never
   stamps a flat `secret_key_base` key). Fixed by moving the check out of
   `PhoenixKit.Supervisor` entirely, into `PhoenixKit.boot/1`
   (`lib/phoenix_kit.ex`), which runs only after `Supervisor.start_link/2`
   returns — i.e. after every child in the host's own tree, Endpoint
   included, regardless of where it's listed. Test:
   `test/phoenix_kit_test.exs`'s new "boot/1 — integrations encryption boot
   check" describe block.

3. **Docs, fixed (contingent on #1)** — `key_rotation.ex`'s and
   `rotate_key.ex`'s "gap between rotating and restarting" sections claimed
   a merge-based write during the gap hits a "loud failure". It never did
   (`Encryption`'s decrypt-failure handling was always a log + silent drop,
   never a raise) — and before the #1 fix, what actually happened was the
   silent, PERMANENT deletion #1 describes, not a loud anything. Reworded
   both to describe the real, POST-fix behavior: reads/silent-drops are
   logged but not exceptions; a write that doesn't touch the stuck field no
   longer destroys it (the #1 fix); a write that DOES supply a fresh value
   for that exact field is still at risk of landing under the stale active
   key, same as the pre-existing "Atomicity and concurrent writers" race.

4. **Test gaps, closed** — added the `:disabled_no_key` case to
   `integrations_encryption_banner_test.exs` (the exact path #2 broke, and
   the only status of the four not covered by that file); added the
   write-survives-a-write test suite (`integrations_encryption_write_safety_test.exs`)
   proving #1's fix by fact, not assertion-on-the-fix-description.

Also fixed, lower-priority items flagged alongside the FAIL (not blocking,
but cheap and closing real gaps in the same area):

- `Encryption`: a 1-character `:integrations_encryption_key` used to report
  as the fully-healthy `:dedicated` tier — no boot warning, no banner, false

  one would.
- `KeyRotation.rotate/2`'s `rotated` count included every row SCANNED, not
