# Claude Review — PR #756

**Title:** Add a key store so a rotated integrations secret is not lost
**Author:** timujinne
**Merge commit:** 201a76b0
**Verdict:** Approve, no changes applied

## Summary

Adds `PhoenixKit.Integrations.KeyStore` (a behaviour with `File`, `S3`, and
`Chain` implementations) so the secret generated by
`mix phoenix_kit.integrations.rotate_key` survives past the terminal it was
printed in, plus a unified `Encryption.key_report/0`/`key_signals/0` verdict
consumed identically by `mix phoenix_kit.doctor`, the boot-time warning, and
the admin settings page.

This is the *n*th round of a documented incident chain (a real key file lost
on 2026-08-18 with an intact-looking but empty value) and the diff itself
narrates roughly five prior review rounds' worth of fixed self-contradictions
(a fingerprint printed next to "no key resolved", a store location claimed as
a backup that wasn't, `{:holding, _}` collapsing two different absences). The
code, moduledocs, and `dev_docs/investigations/*` bundled in this PR reflect
that history in unusual detail.

## Review scope

Read in full: `key_store.ex`, `key_store/file.ex`, `key_store/s3.ex`,
`key_store/chain.ex`, the `Encryption` additions (`key_signals/0`,
`key_report/1`, `key_fingerprint/0`), `phoenix_kit.doctor.ex`'s new check,
`phoenix_kit.integrations.rotate_key.ex`'s store-and-report path, and the
`Live.Settings.Integrations` LiveView + template. Cross-checked the
`resolve_once/0` single-read invariant, the write-then-read-back verification
path, atomic file-write durability (`file.ex`'s temp-file + fsync + rename),
symlink/repository-escape handling, and secret-leak avoidance in error
formatting (`describe_error/1`'s allowlisted tags vs. the tag-only fallback
for unrecognised/third-party error shapes).

## Findings

None at BUG or IMPROVEMENT severity. Specifically checked and found correct:

- **Fail-closed on ambiguous store state.** `write_verified/1` reads back
  after every write and treats a mismatch, an absent value, or a read error
  as failure — never trusts the write's own `:ok`.
- **Decrypt tries the right key during rotation.** `dedicated_candidate/2`
  makes explicit config win over the store deterministically (verified
  against `resolve/3`); `KeyRotation` decrypts under the currently-resolved
  tier before re-encrypting, and the mix task's `--new-key` length check
  (`min_dedicated_key_length/0`) prevents writing a key the app would reject
  on the next boot.
- **No secret ever reaches an error term or a crash log.** `KeyStore.invoke/3`
  catches raised exceptions and keeps only `e.__struct__`, specifically to
  dodge Erlang's crash-report formatting including `apply/3` arguments (which
  for `write/2` is the secret). `describe_error/1` allowlists known tags and
  reduces anything else to its outer tag, so a host-supplied store can't leak
  a secret through an error term it constructs.
- **`File` store durability.** Temp file created with `:exclusive` (rejects a
  planted file), `chmod 0600` before the secret is written (closes the
  default-umask window), `:file.sync/1` on both file and directory before
  reporting success (survives the same crash-mid-write shape as the 2026-08-18
  incident), rename replaces rather than follows a symlink at the target path.
- **Repository-escape check resolves symlinks per path component** rather than
  trusting the lexical `Path.expand/1` result, so a symlinked directory can't
  bypass the "not inside a git working tree" refusal.
- **LiveView wiring is consistent.** `load_encryption_report/1` runs once at
  mount (not on every PubSub-triggered `load_connections/1` reload, which
  would re-pay the ~0.1s PBKDF2 fingerprint cost on unrelated events); no
  leftover references to the old `@encryption_status` assign anywhere in the
  `.ex`/`.heex` pair; the banner's `severity != :ok` guard and the
  fingerprint's tier label agree in every clause checked.
- **Test coverage is unusually rigorous for this kind of state machine.**
  `test/support/key_verdict_invariants.ex` asserts a "real" signal space
  (driven through actual `Application.put_env` + real key files) is a subset
  of the "synthetic" full cross product, specifically because a prior round's
  synthetic-only space (60 combinations, all green) missed a real
  configuration (a too-short secret in the key store) that broke rendering —
  documented as the reason the real space exists at all.

## Not fixed (nothing to fix)

No CRITICAL/HIGH/MEDIUM bugs or IMPROVEMENT-level findings survived review.
One micro-optimization noted and deliberately **not** applied: `key_signals/0`
computes the PBKDF2-HMAC-SHA256 fingerprint (100k iterations, ~0.1 CPU-sec)
unconditionally, even when `mix phoenix_kit.doctor` is run without
`--fingerprint` (the value is just not printed). This is explicit,
documented-in-code trade-off — the module's whole thesis is that the report
must be a pure function of *one* resolution pass so no two fields can
disagree — and skipping the fingerprint computation conditionally would
reopen exactly the class of bug this PR exists to close. Not worth the risk
for a sub-100ms cost on a mix task and an admin-only page mount.

## Post-merge addendum: rotate_rows_query scope gap (found by the PR #759 review)

The parallel review of PR #759 (S015 restricted settings encryption, merged
right after this one) found that `KeyRotation.rotate_rows_query/0` — added
here — only matched `module == "integrations"` rows, silently excluding
PR #759's restricted setting keys (which share this PR's encryption key but
are stored with `module: nil`). See
`dev_docs/pull_requests/2026/759-s015-encrypt-restricted-settings/CLAUDE_REVIEW.md`
for the full writeup. Fixed in this same review sweep: `rotate_rows_query/0`,
`decrypt_all/1`, `has_sensitive_field?/1`, and `rotate_row/3` in
`key_rotation.ex` now branch per row shape (`value_json` map vs. bare
`value` string), backed by a new `Encryption.encrypt_value_with_secret/2`.
