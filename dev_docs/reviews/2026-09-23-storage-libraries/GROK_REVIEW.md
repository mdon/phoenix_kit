The plan's picture of today's Storage module is mostly right, and the line citations still match `fb393135` (HEAD only adds this document). The design breaks on the V201 migration, and it opens private libraries on the current public read path.

## Critical

**V201's library checksum unique index cannot be created on a real install.** Cross-user dedup already stores two file rows with the same `file_checksum` and different `user_file_checksum` values, sharing keys and location rows (`storage.ex:4021-4033`, `clone_file_for_user/5` at `4186`, `clone_file_locations/2` at `4271`). The unique index is on `user_file_checksum` alone (`v135.ex:2558`). V201 puts every existing file into one "Media" library (§9) and replaces that index with `UNIQUE(sha256(library_uuid <> file_checksum))` (§6.4). Both clones hash to the same value, so `CREATE UNIQUE INDEX` fails.

Those rows cannot be collapsed to make the index fit. Other tables point at the file uuid, including `phoenix_kit_comment_media` and `phoenix_kit_cat_pdfs` as `ON DELETE RESTRICT` (`v135.ex:9638`, `v135.ex:9566`) and posts, tickets, annotations, and folder links as `CASCADE` (`v135.ex:5026`, `5458`, `9728`, `8522`). Dropping one clone deletes or blocks on the caller's attachment. The plan calls this drop "additive except" (§9) and does not say which row survives or how foreign keys are repointed.

The same collision includes trashed clones: the current unique index is not partial (`v135.ex:2558`), and `get_file_by_user_checksum/1` does not filter status (`storage.ex:2226`).

## High

**Phase 1 removes uploader access while every existing file sits in one system library.** `authorize_file_read/2` allows the uploader or an Owner/Admin (`file_controller.ex:495-496`). `ImageEditing.allowed?/2` and `AnnotationBurnController.allowed?/3` also allow anyone with the `"media"` key (`image_editing.ex:381-385`, `annotation_burn_controller.ex:116-118`). §6.5 replaces those checks with library membership and says the admin bypass "stays on `Scope.system_role?`". §3.1 then says system libraries are **not** membership-based: access is the `"media"` key only. A normal user who uploaded an avatar or a comment attachment loses the info API and image editing on that file. `/admin/media` is already the whole store, gated by `"media"` (`integration.ex:557`, `auth.ex:2313`), and listings have no user clause (`list_files_in_scope/2` at `storage.ex:1765`).

**User libraries would be world-readable for two releases.** `FileController.show/2` serves anyone who has the token (`file_controller.ex:50-52`). The token is the first 4 hex chars of an MD5 and never expires (`url_signer.ex:137-156`). `get_file_access/1` serves a local hit with `send_file`, proxies `access_type: "private"`, and redirects every other type, including the documented `"signed"`, to `public_url` (`manager.ex:364-401`, `file_controller.ex:1073`). `public_url` is `cdn_url` or `https://{bucket}.s3.{region}.amazonaws.com/...` and ignores `bucket.endpoint` (`s3.ex:81-87`). Phase 1 already creates user libraries and sends new uploads to the user's default library if they have one (§9), while placement stays on the global pool. A public system bucket then redirects private files straight at object storage. §7 and open question 4 postpone the fix until V203.

**The reconciler can delete another library's only copy, or never drain a bucket.** `unreferenced_keys/2` treats a key as live if any instance row still has that `file_name` (`storage.ex:3418-3434`). It does not count `(bucket, key)`. `delete_stored_objects/2` then calls `Manager.delete_file/1`, which deletes that key from every enabled bucket (`storage.ex:3506-3507`, `manager.ex:74-83`). Clones share keys on purpose. After two libraries leave a shared profile at different times, a key-global check either keeps the drained bucket's objects forever (the other library still names the key) or, if the job deletes "this file's old locations" without a per-bucket refcount, removes the other library's bytes.

Tiles make the placement rule in G2 false on the rows themselves. `store_system_file/3` writes a child whose only instance is `variant_name: "original"` and records no locations (`storage.ex:2310-2343`). A rule that places `variant_name == "original"` as an original will put tile pyramids on the originals profile. Tile reads go through `Manager.retrieve_file/2` by key (`file_controller.ex:901`), so a location-based cutover misses every existing tile until something backfills it.

**V202 as written walks every existing object, under a lock the migration style cannot avoid.** §4 copies nothing and does not set `placed_profile_uuid` / `placed_revision`. G6 says a file is stale when those differ from the library's profile. NULL differs, so every file is stale, including every tile and every `store_file/2` original that has no location row (`storage.ex:4700-4718` creates the instance and never calls `create_file_locations/3`). §6.2's fallback probes system buckets on read and backfills. That is one HEAD per bucket per first view, on the serve path.

The schema steps (backfill, `SET NOT NULL`, drop/create unique indexes, swap `fk_files_user_uuid` and the locations bucket FK) run inside Ecto's transactional `use Ecto.Migration`. `SET NOT NULL` takes `ACCESS EXCLUSIVE` and scans the table on PostgreSQL 16 (what CI uses). `CREATE UNIQUE INDEX CONCURRENTLY` cannot run in that transaction. The checksum index that must be dropped is not named `phoenix_kit_files_user_file_checksum_index`. V135 embeds the schema prefix: `#{prefix}_phoenix_kit_files_user_file_checksum_index` (`v135.ex:2558`), which is why `helpers.ex:71` treats it as a 42-byte embedded name.

**`dedup: "off"` cannot coexist with that unique index.** §3.3 stores `"library"` or `"off"`. A unique `(library, checksum)` makes a second row of the same bytes impossible. System-managed rows are in today's unique index too, and identical tile bytes share `user_file_checksum: checksum` (`storage.ex:2321`). The file changeset only names the system dedup index (`file.ex:302-304`), so that collision raises `Postgrex.Error` instead of taking the race path in `insert_or_fetch_system_file/3` (`storage.ex:2387-2394`).

## Medium

**User deletion does not reliably cascade, and V201 does not finish the job.** `anonymize_user_files/1` sets `anonymized_at`, which `File` has no field for (`auth.ex:3837-3855`, schema fields at `file.ex:153-172`). The `rescue` makes the whole `update_all` a no-op, so `user_uuid` is not cleared either. The CHECK `(user_uuid IS NOT NULL) OR (parent_file_uuid IS NOT NULL)` (`v135.ex:9602`) would reject a null uploader on a normal file anyway. `Repo.delete(user)` then hits `fk_files_user_uuid ... ON DELETE CASCADE` (`v135.ex:6412`). It also hits `phoenix_kit_media_folders_user_uuid_fkey` with no `ON DELETE` (`v135.ex:8572-8576`, default NO ACTION) and the two `RESTRICT` file FKs above. Any of those aborts the transaction, so the user and the files stay. When none of them match, the file rows do disappear and `delete_bucket/1` is not involved: nothing calls `delete_stored_objects/2`, so the objects remain (`storage.ex:359-360`). V201 changes only the files FK (§3.1). A user who created a folder still cannot be deleted. `libraries.owner_uuid`, `files.library_uuid`, and `folders.library_uuid` have no `ON DELETE` at all. A trashed library row cannot be removed while `library_uuid` is `NOT NULL` unless the delete cascades into files, which the `RESTRICT` FKs will block.

**G1 and G3 misstate how a file is served.** `get_file_access/1` returns the first local bucket that has the object, and only then considers remotes (`manager.ex:332-347`, `364-371`). Retrieval sorts every enabled bucket by `priority` ascending (`manager.ex:176-179`), so priority `0` is tried before priority `1`. The bucket docs define `0` as the random pool and `1` as highest (`bucket.ex:13-14`). Writes do the opposite: fixed priorities first, then the shuffled pool (`manager.ex:157-167`). With redundancy ≥ 2, local at priority `0` and cloud at priority `1` already writes the cloud first and serves local. The real gap is the one G1 names: there is no "never serve this copy." Backup-only and "serve the CDN even though local has the bytes" are not expressible. `force_bucket_ids` is also capped by `storage_redundancy_copies` and reordered to `list_enabled_buckets()` order (`manager.ex:42-47`, `168-172`), so variants are not actually pinned to every original bucket (`variant_generator.ex:230-240`).

**The object key and the content hash are not what §6.4 and G8 assume.** New uploads land at `{user_uuid[0..1]}/{md5[0..1]}/{md5}/{md5}_original.{ext}` (`storage.ex:4089-4126`). `storage_default_path` is a separate setting (`storage.ex:3174-3175`) and is not part of the key. Local bytes sit under `bucket.endpoint`, default `priv/media` (`local.ex:24`). `Storage.store_file/2` (comment attachments, `annotation_composer.ex:342`) calls `Manager.store_file/1` with no `path_prefix`, so the key is a timestamp plus a random suffix (`manager.ex:250-261`, `storage.ex:4700`). That original instance has no location rows; variants generated immediately afterwards do (`storage.ex:4803-4824`, `variant_generator.ex:347-354`).

`file_checksum` is not one algorithm. `UploadController` hashes with MD5 (`upload_controller.ex:219-225`). The media browser and `Storage.calculate_file_hash/1` use SHA-256 (`media_browser.ex:4221`, `auth.ex:2471-2475`, `storage.ex:4833-4837`). `library_file_checksum = sha256(library_uuid <> file_checksum)` will treat those as different files forever. Same-library dedup also returns the existing row, and `attach_file_to_folder/2` will link it into the uploader's folder (`media_browser.ex:4362-4375`, `storage.ex:2043-2055`). That is safe only while both sides are the same library. A folder link across libraries is otherwise unconstrained (`v135.ex:8522-8540`).

**The V203 credential and SSRF notes are the right problem and miss paths that already connect.** `S3.resolve_credentials/1` calls `Integrations.get_credentials/1` with no owner (`s3.ex:186-188`). The default owner is `:any` (`integrations.ex:295-302`), and a uuid lookup returns the decrypted map before `owner_match?/2`. Only `access_key` and `secret_key` are used; region and endpoint stay on the bucket (`s3.ex:154-167`). `object_storage` is already `[:system, :personal]` (`providers.ex:915-918`). The integration validator connects at save time via `ListBuckets` (`validators.ex:607-618`) and strips `https://` (`validators.ex:718-726`). `S3.aws_config/1` does not strip a scheme (`s3.ex:163-164`), so "take the endpoint from the integration" feeds ExAws a different string than the validator accepted. `cdn_url` is concatenated into the redirect with no host check (`s3.ex:81-83`). A user profile that may include `shareable` system buckets (§3.2) puts that user's objects on a bucket whose `access_type` may be `"public"`. The ownership check is described only inside `resolve_credentials/1`, not on the bucket changeset that stores `integration_uuid` (`bucket.ex:180-207`).

## What is accurate

These claims match the code: folders are unique on `(name, parent)` site-wide (`v135.ex:3962`); organizations are user rows (`user.ex:81`, `auth.ex:1158-1167`) with no org-role table; `FileServer.get_file_location/2` has no callers; the bucket cache is a 5-minute `:persistent_term` entry nothing deletes (`manager.ex:17`, `291-305`); `list_files/1` filters `f.bucket_uuid`, and `File` has no such column (`storage.ex:4674-4675`); `ApplyImageEditJob` stores the render and the backup through automatic selection (`apply_image_edit_job.ex:232`, `299`) and only then writes locations (`508`, `612`); file events go to one topic, `phoenix_kit:media:files` (`storage.ex:133`); V200's index is `(user_uuid, taken_on DESC, taken_at DESC)` under that partial predicate (`v200.ex:55-61`) and nothing in core queries that pair; `storage_default_bucket_uuid` is stored and returned from `get_config/0` (`storage.ex:3134`, `4640-4641`) and is not used when choosing a bucket. `select_buckets_for_storage/2` is a `defp` (`manager.ex:151`).

## A smaller cut

Photos needs a partition, a membership check, and the capture-date index re-keyed. That does not require a new checksum.

Leave `user_file_checksum` in place for V201. Add `library_uuid`, backfill one system library, and keep per-user dedup. Cross-user clones stay legal inside Media, which is what the database already contains. Re-key the capture-date index. Keep uploader-or-membership-or-`"media"` until personal files actually live in a user library.

Do not add storage profiles until a second placement exists. The global settings already are the default profile. Location-based reads, a per-`(bucket, key)` refcount, and a backfill of location rows (tiles and `store_file/2` originals included) have to land before any user bucket is written. They do not have to land before the photos partition.

Do not accept user libraries, or point new uploads at a per-user default, until those files are served as private: no public redirect, and no permanent 4-character token. The open question in §10 is the read path for the feature Phase 1 already turns on.
