# P012 — проверка «Say when the key store is not a copy of the key in use» (ebb9e5c3)

Проверщик: чекер-линия P012, 2026-08-19. Ветка security-integrations-encryption-key.
Контур: только чтение репозитория; Elixir/mix на машине чекера нет, docker-сокет
недоступен — ничего не запускалось, мутации не выполнялись (см. «Ограничение контура»).

## Вердикт: НЕ ПРИНЯТО — один блокер (шестой экземпляр класса, в новом месте)

Заявленная механика P012 (пятое значение оси, `:warn`, четыре поверхности,
совет через условие) — подтверждается чтением, замечаний нет. Но сама правка
`store_state/2` молча поменяла семантику `:holding` → `:shadowed` для ДРУГИХ
состояний (клаузы too_short legacy/none), и в этих состояниях текст совета
«где живёт отвергнутый секрет» стал ложным — при зелёном суите.

## Блокер: неверный адрес ремонта в состояниях `{:legacy|:none, too_short?: true}`

**Файл:** `lib/phoenix_kit/integrations/encryption.ex`
- `store_state/2` (стр. ~372–380): `{:ok, ^key_in_use} -> {:holding}`, `_other -> {:shadowed}`;
- `rejected_secret_location/1` (стр. ~688–691): клауза под `{:holding, location}`
  («either integrations_encryption_key or the secret in …») и fallback
  `rejected_secret_location(_store) -> "integrations_encryption_key"`;
- потребители fallback: `replace_key_action/1` (клауза 527, legacy+too_short) и
  клауза 569 (none+too_short).

**Состояние:** `:integrations_encryption_key` НЕ задан, хранилище держит короткий
секрет (< min), `secret_key_base` задан (или нет — для :none).

**Что происходит:**
1. `resolve/3` → `dedicated_candidate(_config=nil, {:ok, короткий})` →
   `check_dedicated_length` → `:too_short` → tier `:legacy` (secret = secret_key_base)
   или `:none` (secret = nil);
2. `store_state({:ok, короткий}, key_in_use)` — секрет не равен ключу в работе →
   `{:shadowed, location}`. До ebb9e5c3 это был `{:holding, location}`;
3. `rejected_secret_location({:shadowed, _})` падает в fallback →
   `"integrations_encryption_key"`.

**Текст совета в этом состоянии:**
«Replace the rejected secret — integrations_encryption_key. Config wins when it is
set, and while it holds a rejected value the key store is not consulted at all…»

Каждое утверждение ложно: конфиг-ключа НЕТ (нечего заменять и нечему «побеждать»);
отвергнутый секрет лежит в файле хранилища; хранилище КАК РАЗ консультировалось —
оно и есть источник отвергнутого секрета. Оператор идёт править несуществующую
переменную окружения вместо ключевого файла. До правки эта же клауза честно
называла оба источника («either … or the secret in <location>») — комментарий
на стр. ~669–678 прямо документирует это состояние как `{:holding, _}` и
«verified by running».

**Это шестой экземпляр класса из пункта 4 задания:** утверждение о состоянии
(«источник — config») опирается на поведение другого места (`store_state`),
которое изменилось, а посылка не перепроверена. Причём в двух местах сразу:
- комментарий в `encryption.ex` (~стр. 669–691) теперь описывает непроизводимое
  состояние («no config key + 8-char key file gives store: {:holding, _}»);
- комментарий и case в `test/mix/tasks/phoenix_kit_doctor_test.exs`
  (стр. ~380–392): клауза `{:holding, _loc} -> assert "either …"` теперь
  недостижима для целевого состояния, а ветка `_other -> assert "integrations_encryption_key"`
  с зелёным лицом благословляет ложный текст. Тест защищал это место ровно до
  того, как правка P012 сдвинула значение под ним.

**Почему суите зелёный:** обход `test/phoenix_kit/integrations/encryption_test.exs`
(~стр. 1167–1228) использует хранилище только с валидным 40-символьным секретом
и короткий секрет только в конфиге — состояние «короткий секрет В хранилище»
нигде не производится; doctor-перечисление проверяет наличие слова
«integrations_encryption_key» в detail, и ложный текст ему удовлетворяет.

**Как проявится:** оператор с коротким секретом в key-файле увидит
(boot-лог, doctor, баннер) совет заменить `integrations_encryption_key`,
которая у него не задана; правка по совету ничего не меняет, повторные
перезапуски не меняют tier.

**Направление исправления (на усмотрение исполнителя):** `rejected_secret_location/1`
должна различать `{:shadowed, _}` — в legacy/none-тирах shadowed означает
«отвергнутый секрет, вероятно, в хранилище», т.е. это состояние информативнее,
чем старое амбивалентное `:holding`; либо сравнение в `store_state` должно
вестись только для dedicated-тира. Обновить оба комментария и тест
(стр. ~380–392 doctor-теста), добавить production-walk с коротким секретом
в хранилище.

## Проверено по пунктам задания

1. **Поверхности** — все четыре на месте для новой диагностики `{:dedicated, :store_shadowed}`:
   - mix-таск: `key_store_lines` клауза для `{:shadowed, _}` — doctor.ex:255;
     `integration_key_result` собирает detail генерически — ок;
   - страница админки: `encryption_status_title` (integrations.ex:217),
     `encryption_status_detail` (:258), `fingerprint_tier` (:361);
   - загрузочный лог: `warn_if_insecure/0` (encryption.ex:815–822) ветвится по
     severity — `:warn` → `Logger.warning` с полным report-сообщением;
   - баннер: integrations.html.heex:17 `@encryption_report.severity != :ok` —
     срабатывает на `:warn`.
2. **`:warn` вместо `:ok`** — потребителей уровня в lib три: баннер (heex:17),
   `severity_status/1` в doctor (только `:fail` гейтит exit-code, :warn — advisory),
   `warn_if_insecure` (молчит только на `:ok`). Ложных срабатываний не нашёл;
   для ранее-молчаливого dedicated-инсталла с расхождением новый варн — желаемое
   поведение. Ротация разрешается по tier (`Encryption.status/0`, key_rotation.ex:199),
   не по severity — в shadowed-состоянии разрешена, что согласовано с текстом совета.
3. **Совет про ротацию** — обе ветки подтверждены чтением механизма:
   - отказ: `KeyRotation.do_rotate` — `decrypt_all` под активным (конфиговым)
     ключом; строка под хранимым секретом не расшифровывается → rollback, не
     записано ничего (key_rotation.ex, транзакция целиком);
   - замена без копии: ноль строк → `rotate` возвращает ok →
     `store_and_report` → `KeyStore.write_verified` → `Chain.write/2` пишет во
     все члены цепочки без сохранения старого (chain.ex:112–122, rotate-таск
     :253–255). Формулировка соответствует механике.
   - Замечание (не блокер): «refused only while … rows under that secret» чуть
     уже истины — ротация откажет и на любой посторонней битой строке; промах в
     безопасную сторону, текст не становится опасным.
4. **Шестой экземпляр** — найден, см. блокер: посылка «в too_short-состояниях
   `{:holding, _}` означает „источник неоднозначен“» сломана сравнением в
   `store_state/2`. Остальные посылки новой диагностики проверены: оба секрета
   читаются одним проходом (`resolve_once`), сравнение сырых значений корректно
   для dedicated-тира (ключ из хранилища равен прочитанному → `:holding`);
   `{:none}` + `{:ok, валидный}` невозможно (валидный секрет хранилища даёт
   dedicated). Достижимость `{:legacy, :holding}` осталась только в вырожденном
   случае «файл хранилища содержит ровно secret_key_base».
5. **Границы** — подтверждено: пятое значение добавлено в СУЩЕСТВУЮЩИЙ union оси
   `key_store` (типы :302, :326), новых полей/осей нет; правил достижимости в
   `key_report` не добавлено (клаузы только расширились, вердикт остался
   тотальным — doctor-перечисление 60 комбинаций гоняет все). Но отмечу:
   правка сдвинула достижимость в ЧУЖОЙ клаузе (см. блокер) — формально не
   «правило достижимости», а тот же эффект.

## Ограничение контура

Мутационная проверка (убрать сравнение → `{:dedicated, :ok}` в двух именованных
тестах) выполнялась исполнителем; у чекера нет канала записи в /app и нет
Elixir-окружения на хосте — мутация **не проверено мной**, так же как и запуск
суиты (3940/0/1554) — цифра взята из сообщения коммита. Блокер выше установлен
чтением кода и трассировкой `resolve_once → store_state → rejected_secret_location`,
без запуска; для контрольного воспроизведения достаточно
`File.write!(path, "short")` в `holding`-сторе обхода реальных конфигураций.
